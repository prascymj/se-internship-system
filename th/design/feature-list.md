## 1. ติดตามสถานะกระบวนการฝึกงาน

นักศึกษาดูสถานะปัจจุบันของตนเองในกระบวนการฝึกงาน ส่วนอาจารย์/เจ้าหน้าที่ดูภาพรวมสถานะของ
นักศึกษาทั้งหมดในภาคการศึกษาเดียวกันแบบตาราง พร้อมกรองตามสถานะได้ (เช่น ยังไม่ยื่นสถานประกอบการ /
รอนำเสนอ / ผ่านการอนุมัติ / รอเอกสารตอบรับครบ / กำลังฝึกงาน / ถูกส่งตัวกลับ / สิ้นสุดการฝึกงาน)

- รหัสที่เกี่ยวข้อง: [FR-01, FR-02](../requirements/spec.md), [NFR-02](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา (ดูสถานะตนเอง), อาจารย์ที่ปรึกษา/เจ้าหน้าที่ประสานงานฝึกงาน (ดูแดชบอร์ดภาพรวม)
- ระดับความสำคัญ (MoSCoW): Must have

## 2. ยื่นเสนอสถานประกอบการและขออนุมัติ

นักศึกษาบันทึกข้อมูลสถานประกอบการที่ต้องการฝึกงาน นัดวันนำเสนอกับอาจารย์ที่ปรึกษา และรอผลการ
พิจารณา หากไม่ผ่านต้องยื่นสถานประกอบการใหม่และนัดนำเสนอใหม่ได้ซ้ำจนกว่าจะผ่าน เมื่อผ่านแล้วระบบ
เปลี่ยนสถานะนักศึกษาเป็น "พร้อมสมัครฝึกงานที่สถานประกอบการนี้"

- รหัสที่เกี่ยวข้อง: [FR-03, FR-04, FR-05, FR-06, FR-07](../requirements/spec.md), [NFR-02](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา, อาจารย์ที่ปรึกษา/ผู้อนุมัติการฝึกงาน
- ระดับความสำคัญ (MoSCoW): Must have

## 3. ตรวจสอบคุณสมบัติด้านการอบรม

ระบบตรวจสอบว่านักศึกษาเข้าอบรมเตรียมความพร้อมครบตามจำนวนที่กำหนด (ค่าเริ่มต้น 5 ครั้ง ปรับได้)
นักศึกษาอัปโหลด certificate แต่ละครั้งเป็นหลักฐาน และเจ้าหน้าที่/ระบบยืนยันความครบถ้วนก่อนอนุญาตให้
ดำเนินการขั้นถัดไป (ส่งเอกสารสมัครฝึกงาน) ไฟล์ certificate ที่อัปโหลดต้องเป็นประเภท PDF/JPG/PNG และ
ขนาดไม่เกิน 10MB ต่อไฟล์ มิฉะนั้นระบบปฏิเสธการอัปโหลดทันทีพร้อมข้อความแจ้งเหตุผลให้แก้ไข (ไม่รับไฟล์
ไว้ก่อนแล้วค่อยแจ้งภายหลัง)

- รหัสที่เกี่ยวข้อง: [FR-08, FR-09, FR-10](../requirements/spec.md), [NFR-01, NFR-06](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา, เจ้าหน้าที่ประสานงานฝึกงาน
- ระดับความสำคัญ (MoSCoW): Must have

## 4. จัดการเอกสารตอบรับการฝึกงาน 3 ฉบับ

นักศึกษาอัปโหลดเอกสาร 3 ฉบับ (หนังสือขอความอนุเคราะห์ / หนังสือตอบรับ / ใบส่งตัว) ระบบแสดงสถานะ
ว่าเอกสารครบหรือยัง ฉบับใดยังขาด และแจ้งเตือนนักศึกษา/เจ้าหน้าที่เมื่อยังไม่ครบใกล้ถึงกำหนด (ตามนโยบาย
เวลาล่วงหน้าที่ปรับได้ ดูฟีเจอร์ 10) ไฟล์ทั้ง 3 ฉบับที่อัปโหลดต้องเป็นประเภท PDF/JPG/PNG และขนาดไม่เกิน
10MB ต่อไฟล์เช่นเดียวกับ certificate การอบรม มิฉะนั้นระบบปฏิเสธการอัปโหลดทันทีพร้อมข้อความแจ้งเหตุผล

- รหัสที่เกี่ยวข้อง: [FR-11, FR-12, FR-13, FR-14, FR-15](../requirements/spec.md), [NFR-01, NFR-06](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา, เจ้าหน้าที่ประสานงานฝึกงาน
- ระดับความสำคัญ (MoSCoW): Must have

## 5. ปักหมุดสถานประกอบการ วางแผนเส้นทาง และมอบหมายอาจารย์นิเทศ

นักศึกษาปักหมุดตำแหน่งสถานประกอบการที่ฝึกงานบน Google Map ระบบช่วยจัดกลุ่มสถานประกอบการตาม
พื้นที่ใกล้เคียงกันเพื่อสนับสนุนการวางแผนเส้นทางนิเทศ (ระดับ automation ของการวางแผนเส้นทางยังเป็น
สมมติฐานที่ต้องยืนยันกับผู้ใช้ ดู spec หัวข้อ 4 ข้อ 5) จากนั้นเจ้าหน้าที่มอบหมายอาจารย์นิเทศ **1 ท่านต่อ
กลุ่มเส้นทาง** ให้รับผิดชอบ โดยสถานประกอบการทุกแห่งในกลุ่มเดียวกันจะถูกมอบหมายให้อาจารย์ท่านเดียวกัน
ทั้งหมด (ความสัมพันธ์ 1:1 ระหว่างอาจารย์นิเทศกับบริษัทตาม FR-18 — ปรับปรุง 2026-09-16) รองรับการ
มอบหมายด้วยตนเองแม้ยังไม่มี automation เต็มรูปแบบของการจัดกลุ่มเส้นทาง หากเจ้าหน้าที่พยายามมอบหมาย
อาจารย์นิเทศให้กับสถานประกอบการที่มีผู้รับผิดชอบอยู่แล้ว (ขัดกฎ 1:1 ข้างต้น) ระบบต้องไม่ปฏิเสธทันทีและ
ไม่แทนที่อัตโนมัติ แต่ต้องแสดงข้อมูลการมอบหมายเดิมและให้เจ้าหน้าที่ยืนยันการยกเลิก/แทนที่ก่อนจึงจะบันทึก
อาจารย์ท่านใหม่ได้ พร้อมบันทึกประวัติการเปลี่ยนผู้รับผิดชอบ (อาจารย์เดิม → อาจารย์ใหม่, ผู้ทำรายการ, เวลา)
เพื่อการตรวจสอบย้อนหลัง

- รหัสที่เกี่ยวข้อง: [FR-16, FR-17, FR-32, FR-34](../requirements/spec.md), [NFR-04, NFR-02](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา (ปักหมุด), เจ้าหน้าที่ประสานงานฝึกงาน (จัดกลุ่มเส้นทาง/มอบหมายอาจารย์นิเทศ/ยืนยันการแทนที่การมอบหมายเดิม), อาจารย์นิเทศ (รับมอบหมายตามกลุ่มเส้นทาง)
- ระดับความสำคัญ (MoSCoW): Must have

## 6. ให้คะแนนและบันทึกผลสัมภาษณ์ระหว่างนิเทศ

อาจารย์นิเทศ **1 ท่านต่อบริษัท** (ปรับปรุง 2026-09-16) กำหนดรูปแบบการนิเทศแต่ละครั้งว่าเป็น **online
หรือ onsite** ก่อนบันทึกคะแนนตามแบบฟอร์ม/rubric และผลแบบสัมภาษณ์นักศึกษา ไม่ว่าจะเป็นรูปแบบใดก็ตาม
กรณี **onsite** ต้องบันทึกผ่านอุปกรณ์พกพา ณ สถานประกอบการ (แม้สัญญาณอินเทอร์เน็ตไม่เสถียร) โดยเมื่อ
ไม่มีสัญญาณขณะบันทึก ระบบเก็บข้อมูลไว้เป็น local draft บนอุปกรณ์แบบไม่จำกัดเวลาจนกว่าจะซิงก์กับ
เซิร์ฟเวอร์สำเร็จ พร้อม auto-retry อัตโนมัติเมื่อสัญญาณกลับมา และแสดงข้อความ/แบนเนอร์แจ้งเตือนตลอด
ช่วงที่ยังมีข้อมูลค้างซิงก์ (ห้ามลบ draft ทิ้งอัตโนมัติไม่ว่าจะค้างนานเท่าใด) กรณี **online** ไม่บังคับเงื่อนไข
ภาคสนาม/offline ข้างต้น เนื่องจากใช้งานผ่านอุปกรณ์/อินเทอร์เน็ตปกติ (ดูร่างแบบฟอร์ม/rubric/คำถาม
สัมภาษณ์ตัวอย่างใน spec ภาคผนวก หัวข้อ 7 — ยังไม่ใช่ฉบับทางการ)

- รหัสที่เกี่ยวข้อง: [FR-18, FR-19, FR-20, FR-33](../requirements/spec.md), [NFR-03, NFR-07](../requirements/spec.md)
- บทบาทผู้ใช้: อาจารย์นิเทศ (1 ท่านต่อบริษัท)
- ระดับความสำคัญ (MoSCoW): Must have

## 7. ยืนยันการบันทึกข้อมูลกับระบบ internship หลัก

นักศึกษายืนยันด้วยตนเอง (self-declare) ว่าได้บันทึก task/ข้อมูลประจำวันในระบบ internship หลัก
เรียบร้อยแล้ว (ระบบนี้ไม่เชื่อมต่อ API กับระบบเดิมจริง เป็นเพียงการยืนยันด้วยตนเอง — ดูสมมติฐานข้อ 2
ใน spec) ระบบอัปเดตสถานะภาพรวมของนักศึกษาเมื่อได้รับการยืนยัน

- รหัสที่เกี่ยวข้อง: [FR-22, FR-23](../requirements/spec.md), [NFR-02](../requirements/spec.md)
- บทบาทผู้ใช้: นักศึกษา, เจ้าหน้าที่ประสานงานฝึกงาน
- ระดับความสำคัญ (MoSCoW): Must have

## 8. สิ้นสุดการฝึกงานและเอกสารขอบคุณสถานประกอบการ

ระบบเปลี่ยนสถานะนักศึกษาเป็น "สิ้นสุดการฝึกงาน" เมื่อครบระยะเวลา 3 เดือนตามแผน และสร้างหนังสือ
ขอบคุณสถานประกอบการ (ไม่มีลายเซ็น) จากแม่แบบ โดยดึงข้อมูลนักศึกษา/สถานประกอบการที่บันทึกไว้ใน
ระบบ เอกสารที่สร้างต้องตรงตามรูปแบบทางการของมหาวิทยาลัย/สำนักวิชา นอกจากนี้ เมื่อสถานประกอบการ
(host company) ประเมินผลการฝึกงานของนักศึกษาเสร็จสิ้น ระบบต้องแจ้งเตือนนักศึกษาให้ทราบ (milestone:
Workplace Evaluation Completed → Student Notified) เป็นอีก milestone หนึ่งในเฟสสิ้นสุดการฝึกงาน
คู่ขนานกับการเปลี่ยนสถานะและการสร้างหนังสือขอบคุณ — การประเมินจากสถานประกอบการเป็น input คนละส่วน
กับคะแนนอาจารย์นิเทศ และเนื่องจากสถานประกอบการยังไม่มีบัญชีในระบบนี้ เอกสารนี้ตั้งสมมติฐานว่าเจ้าหน้าที่
ประสานงานฝึกงาน/อาจารย์ที่ปรึกษาเป็นผู้บันทึกผลประเมินแทนสถานประกอบการ (ต้องยืนยันกับผู้ใช้ก่อนนำไป
ออกแบบขั้นถัดไป — ดู spec สมมติฐานข้อ 7)

- รหัสที่เกี่ยวข้อง: [FR-24, FR-25, FR-35](../requirements/spec.md), [NFR-02, NFR-05](../requirements/spec.md)
- บทบาทผู้ใช้: เจ้าหน้าที่ประสานงานฝึกงาน (สร้างเอกสาร, บันทึกผลประเมินแทนสถานประกอบการตามสมมติฐาน), อาจารย์ที่ปรึกษา (อาจเป็นผู้บันทึกผลประเมินแทนสถานประกอบการตามสมมติฐาน), นักศึกษา (สถานะที่เปลี่ยน, ผู้รับการแจ้งเตือนเมื่อประเมินเสร็จสิ้น)
- ระดับความสำคัญ (MoSCoW): Must have

## 9. บันทึกและติดตามกรณีปัญหาระหว่างฝึกงาน

ระบบบันทึกวันที่ เหตุผล และผู้บันทึกกรณีนักศึกษาถูกส่งตัวกลับระหว่างการฝึกงาน (เปลี่ยนสถานะเป็น
"ต้องหาสถานที่ฝึกงานใหม่" และย้อนกลับไปยื่นสถานประกอบการใหม่ได้) รวมถึงบันทึกกรณีนักศึกษาที่ผลใกล้
ไม่ผ่านพร้อมวิธีการช่วยเหลือที่ดำเนินการไป และแสดงประวัติ/ไทม์ไลน์กรณีปัญหาของนักศึกษาแต่ละคนตาม
ลำดับเวลาเพื่อการติดตามต่อเนื่อง

- รหัสที่เกี่ยวข้อง: [FR-26, FR-27, FR-28](../requirements/spec.md), [NFR-02](../requirements/spec.md)
- บทบาทผู้ใช้: เจ้าหน้าที่ประสานงานฝึกงาน, อาจารย์นิเทศ
- ระดับความสำคัญ (MoSCoW): Must have

## 10. แจ้งเตือนกำหนดการนำเสนอและนิเทศ

ระบบแจ้งเตือนอาจารย์ที่ปรึกษา/อาจารย์นิเทศเมื่อใกล้ถึงวันนำเสนอสถานประกอบการ หรือกำหนดการนิเทศ
ของนักศึกษาที่ดูแล ตามนโยบายเวลาแจ้งเตือนล่วงหน้าที่เจ้าหน้าที่ปรับได้ (ค่าเริ่มต้นที่แนะนำคือ 7 วัน —
**ยังไม่ใช่ข้อสรุปตายตัว** ผู้ใช้ตอบว่า "ไม่แน่ใจ" เมื่อถูกถามถึงจำนวนวัน ต้องยืนยัน/ปรับอีกครั้งก่อนนำไป
ออกแบบ/พัฒนาจริง) ใช้นโยบายเดียวกันนี้กับการแจ้งเตือนเอกสารที่ยังขาดในฟีเจอร์ 4 ด้วย

- รหัสที่เกี่ยวข้อง: [FR-29, FR-31](../requirements/spec.md)
- บทบาทผู้ใช้: อาจารย์ที่ปรึกษา, อาจารย์นิเทศ
- ระดับความสำคัญ (MoSCoW): Should have
