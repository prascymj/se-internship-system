# ระบบติดตามกระบวนการฝึกงานนักศึกษา (Internship Workflow Tracking System)

> เอกสารฉบับแรกของโปรเจกต์นี้ — บันทึกจาก requirement ดิบที่ได้รับจากผู้ใช้เมื่อวันที่ 2026-09-16
> ยังไม่มีเอกสาร spec อื่นมาก่อนหน้านี้ใน `01-spec/` จึงเริ่มรหัส FR/NFR จาก 01

## 1. บทนำ

โครงการนี้ต้องการพัฒนาระบบสนับสนุนกระบวนการฝึกงาน (internship) ของนักศึกษา ตั้งแต่การประกาศ/ติดตาม
สถานะรายภาคการศึกษา การยื่นเสนอสถานประกอบการและขออนุมัติจากอาจารย์ การตรวจสอบคุณสมบัติก่อนออก
ฝึกงาน การจัดการเอกสารตอบรับ กระบวนการนิเทศระหว่างฝึกงาน 4 เดือน ไปจนถึงเอกสารหลังฝึกงานและการ
บันทึกกรณีปัญหาที่อาจเกิดขึ้นระหว่างทาง

**สำคัญ:** ปัจจุบันมี "ระบบ internship หลัก" อยู่แล้ว ซึ่งนักศึกษาใช้บันทึก task ประจำวันระหว่างฝึกงาน
และสถานประกอบการใช้เข้าไปดูความคืบหน้า ระบบที่กำลังวางแผนในเอกสารฉบับนี้**ไม่ได้แทนที่**ระบบดังกล่าว
แต่ทำงานคู่ขนานกัน โดยเน้นที่ workflow เอกสาร การอนุมัติ การนิเทศ และภาพรวมสถานะของนักศึกษาแต่ละคน
ส่วนการเชื่อมต่อกับระบบเดิมในเอกสารฉบับนี้ยังจำกัดอยู่ที่การให้นักศึกษายืนยันด้วยตนเอง (ดูหัวข้อ
สมมติฐานข้อ 3 และ FR-22–FR-23)

## 2. ขอบเขต (Scope)

### อยู่ในขอบเขต
- การติดตามสถานะกระบวนการฝึกงานของนักศึกษารายภาคการศึกษา (ภาพนี้เริ่มต้นจากบริบท "เทอม 2")
- การยื่นเสนอสถานประกอบการ, การนัดและบันทึกผลการนำเสนอกับอาจารย์, การวนซ้ำเมื่อไม่ผ่าน
- การตรวจสอบคุณสมบัติด้านการเข้าอบรมก่อนฝึกงานและการอัปโหลดหลักฐาน (certificate)
- การอัปโหลดและติดตามเอกสารตอบรับการฝึกงาน 3 ฉบับ (ขอความอนุเคราะห์ / ตอบรับ / ใบส่งตัว)
- กระบวนการนิเทศระหว่างฝึกงาน 4 เดือน: การปักหมุดสถานประกอบการบน Google Map, การจัดกลุ่มเส้นทาง
  นิเทศและมอบหมายอาจารย์นิเทศ **1 ท่านต่อบริษัท** ตามกลุ่มเส้นทางที่รับผิดชอบ (ปรับปรุง 2026-09-16 —
  ดูหัวข้อ 9), การให้คะแนนตามแบบฟอร์ม/rubric และแบบสัมภาษณ์ โดยแต่ละครั้งของการนิเทศระบุรูปแบบได้ว่า
  เป็น **online หรือ onsite**
- การยืนยันการบันทึกข้อมูลในระบบ internship หลัก (self-declare) และการอัปเดตสถานะที่เกี่ยวข้อง
- เอกสารหลังฝึกงาน (หนังสือขอบคุณสถานประกอบการ ไม่มีลายเซ็น)
- การบันทึกกรณีปัญหา: ถูกส่งตัวกลับระหว่างฝึกงาน, กรณีนักศึกษาที่ผลใกล้ไม่ผ่าน

### ไม่อยู่ในขอบเขต (ของเอกสารฉบับนี้)
- การบันทึก task ประจำวันระหว่างฝึกงาน และการที่สถานประกอบการเข้าดูความคืบหน้า — เป็นหน้าที่ของ
  ระบบ internship หลักที่มีอยู่แล้ว ไม่สร้างซ้ำ
- การเซ็นเอกสารแบบดิจิทัล/e-signature — หนังสือขอบคุณสถานประกอบการที่ระบบสร้างไม่มีลายเซ็น
- การจ่ายค่าตอบแทน/สวัสดิการนักศึกษาฝึกงาน
- การกำหนด tech stack ใดๆ — รอการตัดสินใจใน technology stack (ยังไม่ตัดสินใจ) ตามกติกาโปรเจกต์

## 3. บทบาทผู้ใช้ (Roles)

| บทบาท | หน้าที่หลักในระบบนี้ |
|---|---|
| นักศึกษา | ยื่นสถานประกอบการ, อัปโหลดเอกสาร/certificate, ปักหมุด Google Map, ยืนยันการบันทึกในระบบ internship หลัก |
| อาจารย์ที่ปรึกษา/ผู้อนุมัติการฝึกงาน | นัดวันนำเสนอ, บันทึกผลผ่าน/ไม่ผ่านของสถานประกอบการที่นักศึกษาเสนอ |
| อาจารย์นิเทศ (1 ท่านต่อบริษัท ตามกลุ่มเส้นทางที่ได้รับมอบหมาย — ปรับปรุง 2026-09-16) | รับผิดชอบนิเทศบริษัทในกลุ่มเส้นทางของตน (online/onsite), ให้คะแนนตามแบบฟอร์ม/rubric และบันทึกผลแบบสัมภาษณ์ระหว่างนิเทศ |
| เจ้าหน้าที่ประสานงานฝึกงาน | ตรวจสอบเอกสาร/คุณสมบัติ, บันทึกกรณีปัญหา, ดูภาพรวมสถานะทั้งภาคการศึกษา |

> หมายเหตุ: ชื่อบทบาทข้างต้นเป็นการตีความจาก requirement ดิบ ยังไม่ยืนยันกับโครงสร้างสิทธิ์จริงของ
> มหาวิทยาลัย/สำนักวิชา หากมีบทบาทเพิ่มเติม (เช่น หัวหน้าสำนักวิชา, กรรมการ) ต้องปรับปรุงภายหลัง

## 4. สมมติฐานที่ยังไม่ยืนยันกับผู้ใช้ (ต้องทบทวนก่อนนำไปออกแบบขั้นถัดไป)

Requirement ดิบมีหลายจุดที่ตีความได้มากกว่า 1 ทาง เอกสารฉบับนี้เลือกตีความที่สมเหตุสมผลที่สุดไว้ก่อน
เพื่อไม่ให้งานหยุดชะงัก แต่**ทุกข้อต่อไปนี้ต้องได้รับการยืนยันจากผู้ใช้จริงก่อนส่งต่อไปยังขั้น design**:

1. **ผู้อนุมัติผลการนำเสนอสถานประกอบการ (FR-04–FR-05):** สันนิษฐานว่าเป็น "อาจารย์ที่ปรึกษา 1 ท่าน"
   ต่อนักศึกษา 1 คน (single approver) หากในทางปฏิบัติเป็นกรรมการหลายท่านที่ต้องลงมติร่วมกัน ต้องปรับ
   FR-05 ให้รองรับการรวมผลจากหลายท่าน
2. **การเชื่อมโยงกับระบบ internship หลัก (FR-22–FR-23):** สันนิษฐานว่าเป็นการ "ยืนยันด้วยตนเอง"
   (self-declare) ของนักศึกษาเท่านั้น ไม่ใช่การเชื่อมต่อ API/ข้อมูลจริงกับระบบเดิม เนื่องจากยังไม่มี
   ข้อมูลเรื่องสิทธิ์เข้าถึง/technology stack ของระบบเดิม หากภายหลังต้องการเชื่อมต่อจริง ต้องเปิด
   requirement ใหม่แยกต่างหากเมื่อทราบรายละเอียดระบบเดิม
3. **จำนวนครั้งการอบรม (FR-08):** สันนิษฐานว่า "5 ครั้ง" เป็นค่าเริ่มต้นที่เจ้าหน้าที่ปรับเปลี่ยนได้
   ต่อภาคการศึกษา ไม่ใช่ค่าคงที่ hardcode ถาวร
4. **แบบฟอร์มนิเทศ/rubric/คำถามสัมภาษณ์ (ภาคผนวก หัวข้อ 7):** ผู้ใช้ขอให้ร่างเนื้อหาไว้ในเอกสารนี้
   เนื้อหาที่ร่างไว้เป็น**ตัวอย่างเบื้องต้นเท่านั้น** ยังไม่ใช่แบบฟอร์มทางการของสำนักวิชา ต้องให้ผู้ใช้
   ตรวจทาน/ปรับเกณฑ์คะแนนและคำถามก่อนใช้งานจริง
5. **การจัดกลุ่ม/วางแผนเส้นทางนิเทศจากตำแหน่งที่ปักหมุด (FR-17):** ยังไม่ชัดว่าต้องการ automation
   เต็มรูปแบบ (ระบบจัดกลุ่ม/แนะนำเส้นทางอัตโนมัติ) หรือแค่แสดงตำแหน่งบนแผนที่ให้เจ้าหน้าที่วางแผนเอง
   เอกสารนี้ตั้งเป็นระดับ "กลาง" (ไม่ใช่ MVP) ไว้ก่อน โดยกำหนดให้ FR-16 (ปักหมุด) เป็น MVP เท่านั้น
6. **ค่าล่วงหน้าของการแจ้งเตือน (FR-31 ซึ่งขยายความจาก FR-15/FR-29):** เมื่อถูกถามว่าควรแจ้งเตือน
   ล่วงหน้ากี่วันก่อนถึงกำหนด ผู้ใช้ตอบว่า "ไม่แน่ใจ" จึงใช้ค่าเริ่มต้นที่แนะนำคือ **7 วัน** (ปรับได้โดย
   เจ้าหน้าที่ ตามแนวทางเดียวกับ FR-08) ค่านี้**ยังไม่ใช่ข้อสรุปตายตัว** ต้องให้ผู้ใช้ยืนยัน/ปรับอีกครั้ง
   ก่อนนำไปใช้ออกแบบ/พัฒนาจริง
> **หมายเหตุ (2026-09-16, หลังการยืนยัน):** สมมติฐานข้อ 7 เดิม (สถานะของ FR-21/FR-30 หลังปรับ FR-18
> เป็น "อาจารย์นิเทศ 1 ท่านต่อบริษัท") ได้รับคำตอบจากผู้ใช้แล้วว่าให้ **ยกเลิกทั้ง FR-21 และ FR-30**
> จึงตัดออกจากรายการสมมติฐานที่ต้องทบทวน — ดูรายละเอียดผลการตัดสินใจที่
> *(Deprecated — FR-21/FR-30 ยกเลิกจาก scope)* และหัวข้อ 9 ด้านล่าง

## 5. ความต้องการเชิงฟังก์ชัน (Functional Requirements)

### กลุ่ม A: การติดตามสถานะรายภาคการศึกษา (FR-01–FR-02)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|---|---|---|---|
| FR-01 | แสดงสถานะกระบวนการฝึกงานของนักศึกษาแต่ละคน | ระบบต้องแสดงสถานะปัจจุบันของนักศึกษาในกระบวนการฝึกงานประจำภาคการศึกษา (เช่น ยังไม่ยื่นสถานประกอบการ / รอนำเสนอ / ผ่านการอนุมัติ / รอเอกสารตอบรับครบ / กำลังฝึกงาน / ถูกส่งตัวกลับ / สิ้นสุดการฝึกงาน) | สูง |
| FR-02 | แดชบอร์ดภาพรวมสถานะทั้งภาคการศึกษา | เจ้าหน้าที่/อาจารย์ต้องดูภาพรวมสถานะของนักศึกษาทั้งหมดในภาคการศึกษาเดียวกันแบบตาราง พร้อมกรองตามสถานะได้ | สูง |

### กลุ่ม B: การยื่นเสนอสถานประกอบการและการนำเสนอ (FR-03–FR-07)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|---|---|---|---|
| FR-03 | ยื่นข้อมูลสถานประกอบการที่ต้องการฝึกงาน | นักศึกษาบันทึกข้อมูลสถานประกอบการ (ชื่อ ที่อยู่ ผู้ติดต่อ ตำแหน่งงานที่จะฝึก) ผ่านระบบ | สูง |
| FR-04 | นัดวันนำเสนอกับอาจารย์ | ระบบให้บันทึก/นัดวันนำเสนอสถานประกอบการที่เลือกกับอาจารย์ที่ปรึกษา | สูง |
| FR-05 | บันทึกผลการนำเสนอ (ผ่าน/ไม่ผ่าน) | อาจารย์ที่ปรึกษาบันทึกผลการพิจารณาพร้อมความเห็นประกอบหลังวันนำเสนอ (ดูสมมติฐานข้อ 1 เรื่องผู้อนุมัติ) | สูง |
| FR-06 | วนกลับไปยื่นสถานประกอบการใหม่เมื่อไม่ผ่าน | หากผลไม่ผ่าน ระบบต้องให้นักศึกษายื่นสถานประกอบการใหม่และนัดวันนำเสนอใหม่ได้ (ทำซ้ำได้จนกว่าจะผ่าน) | สูง |
| FR-07 | เปลี่ยนสถานะเมื่อผ่านการอนุมัติ | เมื่อผลผ่าน ระบบเปลี่ยนสถานะนักศึกษาเป็น "พร้อมสมัครฝึกงานที่สถานประกอบการนี้" | สูง |

### กลุ่ม C: การตรวจสอบคุณสมบัติด้านการอบรม (FR-08–FR-10)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|---|---|---|---|
| FR-08 | ตรวจสอบจำนวนครั้งการเข้าอบรม | ระบบตรวจสอบว่านักศึกษาเข้าอบรมเตรียมความพร้อมครบตามจำนวนที่กำหนด (ค่าเริ่มต้น 5 ครั้ง ปรับได้โดยเจ้าหน้าที่ — ดูสมมติฐานข้อ 3) | สูง |
| FR-09 | อัปโหลด certificate การอบรม | นักศึกษาอัปโหลดหลักฐาน/certificate การเข้าอบรมแต่ละครั้ง | สูง |
| FR-10 | ยืนยันความครบถ้วนของคุณสมบัติ | เจ้าหน้าที่/ระบบยืนยันผ่าน/ไม่ผ่านด้านคุณสมบัติการอบรม ก่อนอนุญาตให้ดำเนินการขั้นถัดไป (ส่งเอกสารสมัครฝึกงาน) | สูง |

### กลุ่ม D: เอกสารตอบรับการฝึกงาน (FR-11–FR-15)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|---|---|---|---|
| FR-11 | อัปโหลดหนังสือขอความอนุเคราะห์ | นักศึกษาอัปโหลดหนังสือขอความอนุเคราะห์รับนักศึกษาเข้าฝึกงาน | สูง |
| FR-12 | อัปโหลดหนังสือตอบรับ | นักศึกษาอัปโหลดหนังสือตอบรับการฝึกงานจากสถานประกอบการ | สูง |
| FR-13 | อัปโหลดใบส่งตัว | นักศึกษาอัปโหลดใบส่งตัวนักศึกษาเข้ารับการฝึกงาน | สูง |
| FR-14 | ติดตามความครบถ้วนของเอกสารทั้ง 3 ฉบับ | ระบบแสดงสถานะว่าเอกสารทั้ง 3 ฉบับครบหรือยัง ฉบับใดยังขาด | สูง |
| FR-15 | แจ้งเตือนเอกสารที่ยังขาด | ระบบแจ้งเตือนนักศึกษา/เจ้าหน้าที่เมื่อยังมีเอกสารที่ยังไม่ครบใกล้ถึงกำหนด | กลาง |

### กลุ่ม E: กระบวนการนิเทศระหว่างฝึกงาน 4 เดือน (FR-16–FR-20, FR-32–FR-34; FR-21, FR-30 = Deprecated)

| รหัส | ความต้องการ | รายละเอียด | ระดับความสำคัญ |
|---|---|---|---|
| FR-16 | ปักหมุดสถานประกอบการบน Google Map | นักศึกษาปักหมุดตำแหน่งสถานประกอบการที่ฝึกงานบน Google Map เพื่อใช้ในการวางแผนนิเทศ (ใช้ประกอบการวางแผนเส้นทางสำหรับการนิเทศแบบ **onsite** ตาม FR-33 เป็นหลัก — การนิเทศแบบ **online** ไม่จำเป็นต้องอ้างอิงตำแหน่งนี้) | สูง |
| FR-17 | ช่วยจัดกลุ่ม/วางแผนเส้นทางนิเทศ | ระบบช่วยจัดกลุ่มสถานประกอบการตามพื้นที่ใกล้เคียงกัน เพื่อสนับสนุนการวางแผนเส้นทางนิเทศ และเป็นฐานสำหรับการมอบหมายอาจารย์นิเทศตามกลุ่มเส้นทางใน FR-32 (ดูสมมติฐานข้อ 5 เรื่องระดับ automation) | กลาง |
| FR-18 | อาจารย์นิเทศ 1 ท่านต่อบริษัท (ปรับปรุง 2026-09-16) | ระบบกำหนดให้สถานประกอบการ/นักศึกษาแต่ละรายมีอาจารย์นิเทศผู้รับผิดชอบเพียง **1 ท่าน** ตลอดรอบการฝึกงาน (ไม่รองรับการร่วมนิเทศพร้อมกันหลายท่านอีกต่อไป) การมอบหมายอ้างอิงกลุ่มเส้นทางที่จัดไว้ใน FR-17/FR-32 _(เดิม: "รองรับอาจารย์นิเทศหลายท่านต่อรอบ" — แก้ไขตาม requirement ใหม่ 2026-09-16)_ | สูง |
| FR-19 | บันทึกคะแนนตามแบบฟอร์ม/rubric | อาจารย์นิเทศบันทึกผลการให้คะแนนตามแบบฟอร์ม/เกณฑ์ (rubric) ผ่านระบบหลังการนิเทศแต่ละครั้ง ไม่ว่าจะเป็นรูปแบบ online หรือ onsite (ดู FR-33, ภาคผนวก หัวข้อ 7) | สูง |
| FR-20 | บันทึกผลแบบสัมภาษณ์ | อาจารย์นิเทศบันทึกผลแบบสัมภาษณ์นักศึกษา ตามชุดคำถามที่กำหนด ไม่ว่าจะนิเทศแบบ online หรือ onsite (ดู FR-33, ภาคผนวก หัวข้อ 7) | สูง |
| ~~FR-21~~ | ~~สรุปคะแนนรวมจากอาจารย์นิเทศหลายท่าน~~ | **Deprecated (ยกเลิกเมื่อ 2026-09-16)** — เดิม: "เมื่อมีอาจารย์นิเทศมากกว่า 1 ท่านในรอบเดียวกัน ระบบรวม/สรุปคะแนนเป็นคะแนนสรุปต่อรอบนิเทศ" ยกเลิกเพราะ FR-18 เปลี่ยนเป็นอาจารย์นิเทศ 1 ท่านต่อบริษัท จึงไม่มี use case หลายท่านอีกต่อไป (ผู้ใช้ยืนยันแล้ว) รหัสนี้สงวนไว้ไม่นำกลับมาใช้ซ้ำ — ดูเนื้อหาเดิมและเหตุผลเต็มที่ *(Deprecated — FR-21/FR-30 ยกเลิกจาก scope)* | ~~กลาง~~ |
| ~~FR-30~~ | ~~กำหนดคะแนนสรุปแบบเลือกเอง (manual override) เมื่อมีอาจารย์นิเทศหลายท่าน~~ | **Deprecated (ยกเลิกเมื่อ 2026-09-16)** — เดิมขยายความจาก FR-21 (manual override คะแนนโดยเจ้าหน้าที่/อาจารย์หลักเมื่อมีอาจารย์นิเทศหลายท่าน) ยกเลิกด้วยเหตุผลเดียวกับ FR-21 (ผู้ใช้ยืนยันแล้ว) รหัสนี้สงวนไว้ไม่นำกลับมาใช้ซ้ำ — ดูเนื้อหาเดิมและเหตุผลเต็มที่ *(Deprecated — FR-21/FR-30 ยกเลิกจาก scope)* | ~~กลาง~~ |
| FR-32 | มอบหมายอาจารย์นิเทศตามกลุ่มเส้นทาง (ใหม่ 2026-09-16) | เจ้าหน้าที่มอบหมายอาจารย์นิเทศ 1 ท่านให้รับผิดชอบกลุ่มเส้นทาง/พื้นที่หนึ่งกลุ่ม (อ้างอิงการจัดกลุ่มจาก FR-17) สถานประกอบการทุกแห่งในกลุ่มเดียวกันจะถูกมอบหมายให้อาจารย์ท่านเดียวกันทั้งหมด (ความสัมพันธ์ 1:1 ระหว่างอาจารย์นิเทศกับบริษัทตาม FR-18) รองรับการมอบหมายด้วยตนเองแม้ยังไม่มี automation เต็มรูปแบบของ FR-17 | สูง |
| FR-33 | กำหนดรูปแบบการนิเทศ (Online/Onsite) ต่อครั้ง (ใหม่ 2026-09-16) | ระบบให้ระบุรูปแบบการนิเทศแต่ละครั้งว่าเป็น **online** หรือ **onsite** ผูกกับการบันทึกคะแนน/ผลสัมภาษณ์ของครั้งนั้น (FR-19/FR-20) กรณี onsite ต้องอ้างอิงตำแหน่งที่ปักหมุดของสถานประกอบการ (FR-16) และเข้าเงื่อนไขการใช้งานภาคสนาม/offline (NFR-03/NFR-07) กรณี online ไม่บังคับต้องมีพิกัด/เส้นทาง และไม่จำเป็นต้องรองรับ NFR-03/NFR-07 | สูง |
| FR-34 | ยืนยันก่อนแทนที่การมอบหมายอาจารย์นิเทศเดิม (ใหม่ 2026-09-16) | เมื่อเจ้าหน้าที่มอบหมายอาจารย์นิเทศ (FR-32) ให้กับสถานประกอบการที่มีอาจารย์นิเทศผู้รับผิดชอบอยู่แล้ว (ขัดกับกฎ 1:1 ของ FR-18) ระบบ**ต้องไม่ปฏิเสธทันทีและต้องไม่แทนที่อัตโนมัติ** แต่ต้องแสดงข้อมูลการมอบหมายเดิม (ชื่ออาจารย์นิเทศเดิม) และให้เจ้าหน้าที่ (ผู้มีสิทธิ์) **ยืนยันการยกเลิก/แทนที่การมอบหมายเดิมก่อน** จึงจะบันทึกการมอบหมายอาจารย์ท่านใหม่ได้ ระบบต้องบันทึกประวัติการเปลี่ยนผู้รับผิดชอบ (อาจารย์เดิม → อาจารย์ใหม่, ผู้ทำรายการ, เวลา) เพื่อการตรวจสอบย้อนหลังตาม NFR-02 | สูง |

## 6. ความต้องการที่ไม่ใช่เชิงฟังก์ชัน (Non-Functional Requirements)

| รหัส | ด้าน | ความต้องการ |
|---|---|---|
| NFR-01 | ความปลอดภัย/สิทธิ์การเข้าถึงข้อมูล | เอกสารที่อัปโหลด (certificate, หนังสือตอบรับ, ใบส่งตัว) ต้องเข้าถึงได้เฉพาะนักศึกษาเจ้าของข้อมูล อาจารย์ที่เกี่ยวข้อง และเจ้าหน้าที่ที่มีสิทธิ์เท่านั้น |
| NFR-02 | การตรวจสอบย้อนหลัง (Audit) | ทุกการเปลี่ยนสถานะสำคัญ (ผ่าน/ไม่ผ่านการนำเสนอ, ถูกส่งตัวกลับ, สิ้นสุดการฝึกงาน) ต้องบันทึกผู้ทำรายการและเวลาที่ทำรายการ |
| NFR-03 | การใช้งานภาคสนาม | อาจารย์นิเทศต้องสามารถบันทึกคะแนน/ผลสัมภาษณ์ผ่านอุปกรณ์พกพา ขณะอยู่ ณ สถานประกอบการ ซึ่งอาจมีสัญญาณอินเทอร์เน็ตไม่เสถียร **(บังคับใช้เฉพาะการนิเทศแบบ onsite ตาม FR-33 — การนิเทศแบบ online ไม่อยู่ในเงื่อนไขนี้ เพราะใช้งานผ่านอุปกรณ์/อินเทอร์เน็ตปกติ)** |
| NFR-04 | ประสิทธิภาพการแสดงผลแผนที่ | การแสดงตำแหน่งปักหมุดสถานประกอบการของนักศึกษาทั้งรุ่นบนแผนที่ต้องไม่หน่วง แม้มีจำนวนหมุดมาก |
| NFR-05 | ความถูกต้องของเอกสารที่สร้างอัตโนมัติ | หนังสือขอบคุณสถานประกอบการที่ระบบสร้างต้องตรงตามรูปแบบทางการของมหาวิทยาลัย/สำนักวิชา |
| NFR-06 | ความถูกต้องของไฟล์ที่อัปโหลด (File Validation) | ทุกจุดที่ให้อัปโหลดไฟล์ในระบบ (certificate การอบรม FR-09, หนังสือขอความอนุเคราะห์/หนังสือตอบรับ/ใบส่งตัว FR-11–FR-13) ต้องรับเฉพาะไฟล์ประเภท PDF และรูปภาพ (JPG/PNG) ขนาดไม่เกิน 10MB ต่อไฟล์ หากผู้ใช้อัปโหลดไฟล์ผิดประเภท เกินขนาด หรือไฟล์เสีย ระบบต้อง**ปฏิเสธการอัปโหลดทันที** พร้อมแสดงข้อความแจ้งเหตุผลที่ชัดเจนให้ผู้ใช้แก้ไข (ไม่รับไฟล์ไว้ก่อนแล้วค่อยแจ้งภายหลัง) |
| NFR-07 | การทำงานแบบออฟไลน์และการซิงก์ข้อมูล (Offline Draft & Auto-Sync) | ขยายความจาก NFR-03: เมื่อไม่มีสัญญาณอินเทอร์เน็ตขณะบันทึกคะแนน/ผลสัมภาษณ์ภาคสนาม (เฉพาะการนิเทศแบบ **onsite** ตาม FR-33) ระบบต้องเก็บข้อมูลไว้เป็น local draft บนอุปกรณ์**ไม่จำกัดเวลา**จนกว่าจะซิงก์กับเซิร์ฟเวอร์สำเร็จ พร้อม auto-retry อัตโนมัติเมื่อสัญญาณกลับมา และแสดงข้อความ/แบนเนอร์แจ้งเตือนผู้ใช้ตลอดช่วงที่ยังมีข้อมูลค้างซิงก์ ห้ามลบข้อมูล draft ทิ้งอัตโนมัติไม่ว่าจะค้างนานเท่าใดก็ตาม |

## 7. ภาคผนวก: ร่างแบบฟอร์มนิเทศและแบบสัมภาษณ์ (Draft — ยังไม่ยืนยัน)

> ร่างนี้จัดทำขึ้นเพื่อตอบสนองคำขอ "แบบฟอร์ม และคำถาม" ในความต้องการดิบ เป็นเพียงตัวอย่างเบื้องต้น
> อ้างอิงรูปแบบทั่วไปของแบบประเมินการนิเทศฝึกงาน **ต้องให้ผู้ใช้ตรวจทาน ปรับเกณฑ์คะแนน และคำถามให้
> ตรงกับแบบฟอร์มทางการของสำนักวิชาก่อนใช้งานจริง** (เกี่ยวข้องกับ FR-19, FR-20)

### 7.1 ข้อมูลทั่วไปของการนิเทศ
- ชื่อนักศึกษา / รหัสนักศึกษา
- ชื่อสถานประกอบการ / ที่อยู่
- วันที่นิเทศ / ครั้งที่นิเทศ
- ชื่ออาจารย์ผู้นิเทศ (อาจมากกว่า 1 ท่าน)

### 7.2 เกณฑ์การให้คะแนน (Rubric ตัวอย่าง คะแนนเต็มข้อละ 5)

| ด้านที่ประเมิน | คำอธิบาย | คะแนนเต็ม |
|---|---|---|
| ความรู้และทักษะทางวิชาชีพที่นำไปใช้ปฏิบัติงานจริง | นักศึกษาประยุกต์ความรู้ที่เรียนมาใช้ในงานที่ได้รับมอบหมายได้เหมาะสมเพียงใด | 5 |
| ความรับผิดชอบและการตรงต่อเวลา | การเข้างานตรงเวลา ความรับผิดชอบต่องานที่ได้รับมอบหมาย | 5 |
| การทำงานร่วมกับผู้อื่น/การสื่อสาร | การปรับตัวเข้ากับวัฒนธรรมองค์กร การสื่อสารกับพี่เลี้ยง/ทีมงาน | 5 |
| การแก้ปัญหาและความคิดริเริ่ม | ความสามารถในการแก้ปัญหาเฉพาะหน้า และการเสนอแนวคิดใหม่ | 5 |
| บุคลิกภาพและจรรยาบรรณวิชาชีพ | การแต่งกาย มารยาท จรรยาบรรณในการทำงาน | 5 |
| ความก้าวหน้าของงานเทียบกับแผนที่วางไว้ | งานที่ทำสำเร็จเทียบกับแผนงานที่ตกลงไว้ตอนต้น | 5 |
| **รวม** | | **30** |

### 7.3 แบบสัมภาษณ์ (คำถามปลายเปิด ตัวอย่าง)
1. งานที่ได้รับมอบหมายสอดคล้องกับสาขาที่เรียนหรือไม่ อย่างไร
2. อุปสรรคหรือปัญหาที่พบระหว่างฝึกงาน และมีวิธีการแก้ไขอย่างไร
3. สิ่งที่ได้เรียนรู้เพิ่มเติมนอกเหนือจากในห้องเรียนคืออะไร
4. ความคิดเห็นของพี่เลี้ยง/หัวหน้างานต่อการปฏิบัติงานของนักศึกษา (สอบถามฝ่ายสถานประกอบการ)
5. มีความประสงค์จะร่วมงานกับสถานประกอบการนี้ต่อหลังจบการศึกษาหรือไม่

### 7.4 สรุปผลการนิเทศ
- คะแนนรวม / ระดับผลการประเมิน
- ข้อเสนอแนะจากอาจารย์ผู้นิเทศ
- ลงชื่ออาจารย์ผู้นิเทศ (ในระบบ ไม่ใช่ลายเซ็นจริงบนกระดาษ)

## 10. ส่วนขยาย: Edge case การมอบหมายอาจารย์นิเทศซ้ำบริษัทเดิม (เพิ่มเมื่อ 2026-09-16)

ระหว่างที่ subagent `test-writer` เขียน test case ของ FR-32 พบ edge case ที่ spec เดิมยังไม่นิยาม:
กรณีเจ้าหน้าที่พยายามมอบหมายอาจารย์นิเทศ "ท่านที่ 2" ให้บริษัทที่มีอาจารย์นิเทศผู้รับผิดชอบอยู่แล้ว 1
ท่าน (ขัดกฎ 1:1 ของ FR-18) ผู้ใช้ (อาจารย์) ตัดสินใจผ่าน UI ว่าระบบต้องให้ผู้มีสิทธิ์ยืนยัน/ยกเลิกการ
